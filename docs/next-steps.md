## 项目判断

当前项目适合作为数字商品、卡密兑换和代理发卡平台的 MVP。账户、钱包流水、卡密一次性交付、公开兑换、代理采购、团队统计、审计、队列和站内监控已经形成闭环。

当前运行配置仍是本机开发演示环境：`APP_ENV=development`、`FULFILLMENT_MODE=mock`，演示充值和模拟履约不能代表真实 ChatGPT 充值。授权履约分支目前是失败闭锁占位，不会向外部服务商发请求。

## 推荐路线

### P0：先确定可销售的履约方式

优先选择以下两种方式之一：

1. **卡密销售模式**：平台只生成、销售和兑换由平台控制的数字权益，不处理客户 Session、Cookie、密码、CVV 或完整银行卡号。
2. **正式授权服务商模式**：客户在官方页面或授权页面完成登录和支付授权，平台只接收短期授权引用、订单状态和回执。

在没有正式服务商合同、API 文档、沙盒账号和回调规范前，继续使用 `manual` 或 `mock`，不要把 `authorized` 标记为已接入。

### P0：取得服务商接入资料

必须确认商品 ID、地区、价格、授权方式、幂等键、限流、查询接口、取消续费、移除支付方式、退款、Webhook 签名、重试、对账文件、数据保留和人工介入规则。缺少任一项时，对应操作应保持待人工处理。

### P0：实现真实履约的技术隔离

正式接入时新增独立 provider client 和 durable outbox：

- 订单事务先写 outbox，再由 worker 发送；
- 每个订单固定供应商幂等键，重试不重复开通；
- Webhook 校验签名、时间戳和事件 ID，拒绝重放和乱序覆盖；
- 取消、退款和删除支付方式使用独立状态机和二次确认；
- 供应商账单与平台钱包流水定期对账，差异进入人工队列；
- 日志、审计和监控不记录 Session、Cookie、密码、CVV 或完整卡号。

### P0：补齐真实支付

演示钱包不能直接替代收款。真实上线前需要支付预订单、验签回调、支付超时、重复回调、退款、渠道差错和对账。余额充值与卡密采购要分别定义资金状态，不能用管理员调整接口代替真实收款。

### P1：生产运维和安全

- 使用私有 GitHub 仓库、分支保护、版本标签和 secret scanning；当前目录没有 Git 历史，不利于回滚和审计。
- 生产使用 HTTPS 域名、外部 PostgreSQL、Redis 高可用或托管服务、密钥管理、异地加密备份和定期恢复演练。
- 增加主机或云监控，监控错误率、队列积压、worker 心跳、对账差异、数据库容量和备份结果。
- 增加 MFA、敏感操作二次确认、设备会话管理和更明确的风控规则。
- 将 8080 与 8081 明确标记为开发/对照环境，避免两套数据被误认为同一生产库。

### P1：产品和运营

- 先完成“代理采购卡密 → 客户公开兑换 → 订单查询 → 账单报表”的主路径验收。
- 明确商品成本、售价、代理折扣、退款责任和客服处理时限。
- 佣金、多级代理、授信和利润报表放到真实销售规则确定后再做，避免先实现错误的结算口径。
- 跨浏览器、键盘导航、屏幕阅读器和真实移动设备验收完成后再扩大用户范围。

## 暂缓事项

不要实现接收客户真实 Session 后代登录、代付、取消续费或删除支付方式的接口；这会把平台变成高风险凭据代理，也无法用“只临时保存”消除风险。不要抓取或复制参考站的非公开接口，也不要把 mock 订单或演示余额展示为真实充值成功。

## 建议的上线闸门

只有在真实支付沙盒、服务商沙盒、签名回调、重试幂等、退款、对账、备份恢复、外部监控和安全评审全部通过后，才切换到生产配置。否则项目保持当前 MVP 演示和卡密销售范围。
